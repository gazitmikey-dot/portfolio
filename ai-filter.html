AI Natural
Language Filter

Filtering the vendors table is one of the most frequent workflows on the Findings platform. Compliance officers managing dozens to hundreds of third-party vendors need to quickly surface specific subsets — vendors with a certain risk level, in a particular review stage, or tied to a specific framework. The AI filter lets users describe what they want in plain language instead of building structured query rows. But adding a new interaction model alongside an existing one raises a set of UX questions that need deliberate answers: can the two modes coexist? What does switching between them mean? What gets lost when the user walks away?

My Role & Context

I led the UX for this feature end-to-end — defining the interaction model, designing all states and edge cases, and delivering a full Figma handoff to the development team. I also built an interactive HTML prototype to validate the experience before engineering began.

When I joined the project, a working prototype already existed alongside a markdown technical requirements file — both built by the developer. I took those as my starting point, using Claude Code to explore possible directions and Figma for the pixel-perfect UI design. It wasn't a blank slate — but having a starting point isn't the same as having the right design. The UX decisions made along the way took the feature somewhere that first prototype never reached.

The Problem

The challenge wasn't designing an AI filter — it was adding one to a system that already existed. The platform had one filter button, one apply action, one active filter state. Introducing AI meant adding a completely different interaction paradigm into a surface compliance teams use every day.

The risk was fragmentation: two filter buttons, two apply mechanisms, two separate "filter is active" states. Users would need to mentally track two parallel systems for what is ultimately one action — narrowing down a table. Getting this wrong would make the feature feel like two disconnected tools bolted together rather than one coherent system.

Challenge 1

The "or" decision — and the architecture it created

The backend technically can translate a natural language prompt into existing system filter fields. This raised the idea of showing the AI result and the equivalent standard filter side by side — "here's what I understood, here's how it looks in standard mode." The idea was tempting because it felt transparent.

But it was rejected. AI can produce filters that have no equivalent in the standard field system. The moment some conditions are editable in standard mode and others aren't, the interface becomes unpredictable. The only clean solution: a hard "or" — one mode at a time, always. Because only one mode can be active, the product keeps one filter button, one apply action, one active state. No fragmentation.

Decision The "or" is communicated upfront in the router popover with hint text: "Choosing one will clear the other."

The "or" directly shaped the architecture. Two separate modes need two dedicated spaces — a single combined panel would imply they're interchangeable. The solution: three popovers. A router that opens first and presents the choice; an AI chat popover for conversational filter-building; and a standard filter popover for structured rows. One entry point, two dedicated spaces behind it.

Challenge 2

Why a popover, not a drawer

Once the decision was made to build the AI chat as its own dedicated space, the natural instinct was to use a drawer — the sliding side panel pattern that's become the standard for AI chat interfaces. Cursor, GitHub Copilot, Claude Code — they all use a drawer. It's what users associate with "chat with AI."

A drawer was designed and reviewed. It worked. The height was generous, the conversation had room to breathe, and the familiar pattern would reduce the learning curve. But it was still rejected.

Drawer

Slides in from the side. Persists across the page while open. Suggests a persistent assistant that can help you with anything — navigate to other sections, answer questions, take action across the product.

Popover ✓

Anchored to the filter button. Contained and contextual. Disappears when done. Suggests a focused tool that does one thing: helps you build a filter for this table, right now.

Decision The component needs to communicate its scope before the user reads a single word. A drawer implies an agent. This is a filter tool.
Challenge 3

Generative UI — the chat isn't just text

A purely text-based chat requires the user to type every answer. For a clarifying question like "by critical findings, do you mean: only Critical risk level, or Critical and Show Stopper?" — making the user type one of those options back is unnecessary friction and easy to get wrong.

The decision was to extend the scope of the feature to include generative UI: when the AI asks a clarifying question, it renders the options as clickable chips directly in the chat. The user can read the question, scan the options, and click the one they want — no typing required. The AI receives the selection and continues the conversation exactly as if the user had typed it.

Decision Clickable option chips make the conversation significantly easier to navigate — especially for compliance officers who may be asking complex filter queries with multiple clarification steps. The chips also make the AI's questions easier to read: numbered, visually distinct, and scannable rather than buried in a paragraph of text.

Two rules govern how the chips behave:

  • Chips are one-time only. Once the user selects an option, all chips in that group become inactive — visually they remain as a record of what was answered, but they can no longer be clicked. This prevents mid-flow changes that would create an inconsistent or contradictory filter. The conversation moves forward; it doesn't loop back.
  • The Apply Filter button is progressive. It only appears once the AI has finished clarifying and presents its summary — the "Here's what I understood" step with the filter pills. Not at the start, not between clarifying questions. The button appearing is itself a signal: the AI believes it has understood the request and is ready to run it. The user still has the final say before anything changes on the table.
Challenge 4

After Apply — getting back in and reusing past filters

Once an AI filter is applied, the feature needs to answer two questions: how does the user get back into the conversation to refine or clear it, and how do they reuse a filter they've run before without rebuilding it from scratch?

Getting back in. When a filter is active, the filter button in the toolbar shows the AI sparkle icon with a count badge. Clicking it re-opens the AI chat popover — not a fresh state, but the existing conversation, showing the filter that was applied and confirming it's still active. From there the user can type a follow-up to refine the filter, clear it, or switch to standard. The popover is the single entry point — no second place to manage the active filter.

Recent filters (history). The history icon in the popover header opens a recent filters list. This is not a chat replay — it shows the applied filter results from past sessions as cards the user can quickly recognize and reapply. Storing full conversations would be technically expensive and not actually useful; what compliance officers need is to recall and rerun a filter, not to re-read the dialogue that built it.

Decision History stores the filter output only — what conditions were applied — not the conversation that produced it. Each card shows the filter description in plain language so it's scannable at a glance. Selecting one and clicking Apply is a swap: it replaces the current active filter. No merging, no stacking — consistent with the "one mode, one filter" principle throughout the feature.

Persistence rule. Closing the AI popover never clears the conversation — only the explicit "New Chat" button does. Clicking outside (backdrop) on the AI popover intentionally does nothing, because a multi-turn conversation is deliberate work that shouldn't be lost by an accidental click. This is the one place in the feature where the popover behaves differently from the router and standard filter popovers, which do close on backdrop click.

Conclusion

The hardest decisions on this project weren't about the AI itself — they were about integration. How do you add a completely different interaction paradigm to a system that already exists, without fragmenting the UI or confusing the people who use it every day?

The "or" decision answered that. One mode at a time, one filter button, one apply action. Everything else — the three-popover architecture, the popover-not-drawer choice, the generative UI chips, the history model — followed from that foundation.

Working through these decisions led to a result that looked almost nothing like the first prototype. The "or" architecture, the three-popover structure, the popover-not-drawer choice, the generative UI chips, the history model — none of that came from the AI-coded version. It came from thinking through the actual user problems. The AI-coded prototype solved the feature. The UX process solved the experience.
